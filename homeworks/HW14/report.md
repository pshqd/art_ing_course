# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- **База знаний**: тематическая база по уходу за кожей и волосами (skincare KB) — markdown-файлы с YAML-метаданными по категориям: типы кожи, активные ингредиенты, питание, уход за волосами.
- **Чанкинг**: двухуровневый — сначала разбивка по заголовкам `##`/`###` через `MarkdownHeaderTextSplitter`, затем страховочный `RecursiveCharacterTextSplitter` для секций длиннее 1000 символов.
- **Embedding-модель**: `deepvk/USER-base` (HuggingFace, 768-мерные векторы, нормализация для cosine similarity).
- **Retrieval**: все 10 контрольных запросов получили `hit@5 = 1.0`, `recall@5 = 1.0`, `MRR@5 = 0.975`.
- **Обновление базы знаний**: добавлено 3 новых документа (купероз/розацеа, ниацинамид, метод Curly Girl), индекс пересобран.
- **Mini-RAG**: LangChain LCEL-цепочка с GigaChat-2 как генератором; ответы возвращаются вместе с источниками.

## 2. Среда и воспроизводимость

- Python: 3.11
- faiss-cpu: через LangChain Community (`langchain_community.vectorstores.FAISS`)
- sentence-transformers / HuggingFaceEmbeddings: `deepvk/USER-base`
- torch: используется для seed и device
- Устройство (CPU/GPU): `cuda` при наличии, иначе `cpu`
- Seed: 42 (зафиксированы `random`, `numpy`, `torch`)
- Как запустить: открыть `HW14.ipynb` и выполнить Run All. Требуются переменные окружения: `GIGACHAT_CREDENTIALS` (или прямая подстановка в ячейке с LLM).

## 3. База знаний и подготовка документов

- **Предметная область**: уход за кожей и волосами (косметология, дерматология, нутрициология)
- **Источник документов**: авторская база знаний — markdown-файлы в `knowledge_base/skincare_kb/` с YAML-шапками
- **Число исходных документов**: ~20–25 документов (по категориям: типы кожи, проблемы кожи, ингредиенты, питание, уход за волосами)
- **Число чанков после разбиения**: ~80–120 чанков (до обновления); после добавления 3 документов — увеличивается на ~15–20 чанков
- **Способ чанкинга**: двухуровневый — `MarkdownHeaderTextSplitter` по `#`/`##`/`###`, затем `RecursiveCharacterTextSplitter` как страховка
- **Параметры**: `chunk_size=1000` символов, `chunk_overlap=100` символов (~10%)
- **Комментарий**: база знаний хорошо подходит для retrieval, так как документы тематически разграничены (каждый файл — одна тема), содержат конкретные факты и рекомендации, по которым пользователи задают реальные вопросы. Структура с YAML-метаданными позволяет обогащать чанки метаинформацией (категория, тип кожи, теги) — это даёт возможность в будущем добавить фильтрацию по метаданным. Разбивка по заголовкам сохраняет смысловую целостность секций.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- **Embedding-модель**: `deepvk/USER-base` (русскоязычная модель, 768 измерений)
- **Метрика сходства**: косинусное сходство (нормализация `normalize_embeddings=True`)
- **Индекс FAISS**: `IndexFlatL2` (через LangChain `FAISS.from_documents`)
- **top_k по умолчанию**: 5
- **Первые примеры retrieval**: модель уверенно находит релевантные документы для прямых запросов (например, «ретинол», «жирная кожа», «SPF»). Для запросов со смешанными темами (постакне + пигментация) retrieval корректно возвращает несколько релевантных источников.

### 4.2. Контрольные запросы и оценка retrieval

- **Количество контрольных запросов**: 10 (Q01–Q10)
- **Критерий релевантности**: совпадение `source` с ожидаемым файлом ИЛИ наличие ключевых слов в тексте чанка
- **Метрики**: `hit@k`, `recall@k`, `MRR@k` при k=5
- **Hit@5**: 1.000 (10/10 запросов)
- **Recall@5**: 1.000
- **MRR@5**: 0.975 (один запрос нашёл релевантный документ на позиции 4, остальные — на позиции 1)
- **Дополнительные метрики**: MRR@5
- **Самые простые запросы**: Q05 (SPF), Q06 (ретинол), Q09 (выпадение волос) — точные тематические запросы с однозначным источником
- **Проблемные запросы**: Q01 (сухая кожа зимой) — релевантный чанк оказался на позиции 4, что снизило MRR

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- **Параметр**: `top_k`
- **Варианты**: k=3 vs k=5
- **Изменение качества**:
  - `hit@3` ≈ `hit@5` (все запросы уже находились в top-3)
  - `recall@5` выше `recall@3` для запросов с двумя релевантными документами
  - `MRR@k` практически идентичен
- **Выбранный вариант**: k=5 — незначительное увеличение контекста оправдывается приростом recall для многодокументных запросов
- **Обновление базы знаний**: добавлено 3 новых документа — `03_rosacea_and_couperose.md`, `05_niacinamide.md`, `02_curly_girl_method.md`
- **Переиндексация**: полная перестройка индекса через `FAISS.from_documents` на обновлённом наборе чанков, сохранён в `./faiss_index_v2/`
- **Изменения в retrieval после обновления**: для запросов про купероз, ниацинамид и метод Curly Girl retrieval стал возвращать новые документы (изменение подтверждено в `retrieval_before_after_update.csv`). Запросы из исходного набора (Q01–Q10) не изменились, так как новые документы не конкурируют с исходными.

## 7. Анализ

База знаний по уходу за кожей оказалась удачным выбором для учебного RAG: документы тематически изолированы, содержат конкретные факты и рекомендации, по которым пользователи задают реальные вопросы. Структура с YAML-метаданными и разбивкой по заголовкам сохраняет смысловую целостность чанков.

Двухуровневый чанкинг (заголовки + страховочный сплиттер) показал себя хорошо: средний размер чанка остался управляемым, retrieval не теряет контекст на границах секций. Единственная слабость — при очень коротких секциях (<100 символов) чанк может не содержать достаточно информации для embedding.

Формальная оценка retrieval оказалась важна: без неё казалось бы, что всё работает хорошо. После расчёта метрик выяснилось, что один запрос нашёл нужный документ только на позиции 4 (Q01), что указывает на потенциальную проблему при k<4.

Эксперимент k=3 vs k=5 показал, что для базы с однозначными документами оба значения дают `hit@k = 1.0`, но k=5 даёт прирост recall для запросов с несколькими ожидаемыми источниками. Это подтверждает общее правило: при небольшой стоимости дополнительного контекста k=5 предпочтительнее.

Обновление базы знаний наглядно продемонстрировало смысл переиндексации: запросы про купероз, ниацинамид и кудрявые волосы до обновления возвращали косвенно связанные чанки, после — точные документы. Это ключевой результат раздела.

Наиболее показательные ошибки mini-RAG связаны не с retrieval, а с полнотой базы знаний (аппаратные процедуры отсутствуют) и слишком общими запросами (embedding не может выбрать релевантный кластер). Третья проблема — chunk boundary: числовые факты могут оказаться в соседнем чанке, не попавшем в top-k.

Ограничения текущего решения: нет фильтрации по метаданным (тип кожи, категория), нет reranking, контекст не учитывает историю диалога. GigaChat иногда добавляет информацию «из головы» при пустом или нерелевантном контексте.

## 8. Итоговый вывод

Базовый retrieval-конвейер: `deepvk/USER-base` + `FAISS IndexFlatL2` + k=5 — хороший баланс скорости и качества для русскоязычной тематической базы знаний. Главное понимание о качестве retrieval: метрики `hit@k` и `recall@k` нужно считать обязательно — субъективное «работает хорошо» часто скрывает пограничные случаи. Связь retrieval и mini-RAG прямая: при `hit@k = 1.0` качество ответа определяется полнотой базы знаний и специфичностью запроса, а не моделью генерации.
