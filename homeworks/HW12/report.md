# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался датасет `S12-hw-dataset.csv` с дневным временным рядом; прогнозировалось следующее значение колонки `target` (горизонт = 1 день).
- Данные разбиты хронологически: 70% train / 15% validation / 15% test — без перемешивания строк.
- Сравнивались четыре подхода: B1 (naive-last), B2 (moving average), B3 (Ridge на лаговых признаках), R1 (GRU на оконном представлении).
- Лучшим оказался **B3 (Ridge)** с val_MAE = 5.36: богатый набор лаговых и rolling-признаков позволил линейной модели превзойти как простые baseline, так и GRU на данном ряде.

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: дневная

Присутствуют отдельные пиковые выбросы, которые усложняют прогноз и увеличивают RMSE. Нестационарность умеренная: дисперсия остаётся относительно стабильной на протяжении всего периода.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: функция `temporal_split` делит DataFrame по индексам без перемешивания — train идёт первым, за ним validation, затем test.
- Какие доли или интервалы использовались: 70% / 15% / 15% по числу строк.
- Почему `random split` здесь некорректен: при случайном разбиении модель видит в обучении наблюдения из периодов, хронологически позже тестовых. Это создаёт утечку информации из будущего (data leakage): метрики на валидации оказываются завышены, а реальное качество на продакшн-данных будет значительно хуже.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: lag_1, lag_2, lag_3, lag_5, lag_7, lag_10, lag_14, lag_21, lag_28, lag_35, lag_42
- Какие rolling-признаки использовались: rolling_mean, rolling_std, rolling_max, rolling_min, rolling_range по окнам 3, 7, 14, 28; EWM с alpha=0.3 и 0.1; разности diff_1, diff_7, diff_28
- Какие календарные признаки использовались: dayofweek, month, dow_sin, dow_cos, month_sin, month_cos
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN удалялись через `dropna()` — это неизбежные потери первых ~42 строк из-за максимального лага.
- Использовалось ли масштабирование и где именно оно обучалось: да, `StandardScaler` для признаков B3 обучался только на `X_train`, затем применялся к val и test. Отдельный `StandardScaler` для таргета GRU — аналогично только на `train_df`.

## 5. Модели и эксперименты (B1, B2, B3, R1)

- B1 (`naive-last`): предсказывает последнее значение train для всего val/test. Не обучается, служит нижней границей качества.
- B2 (`moving-average`): усредняет последние 7 значений из скользящего окна. Учитывает локальный тренд, но не сезонность.
- B3 (`ridge-lag-features`): RidgeCV с подбором alpha через TimeSeriesSplit(n_splits=5) на 41 признаке (лаги + rolling + EWM + diff + календарь). Best alpha = 0.1.
- R1 (`gru-forecast`): GRU с hidden_size=64, num_layers=2, dropout=0.2 на оконном представлении длины 56. Обучался с CosineAnnealingLR, clip_grad=1.0, early stopping (patience=10).

Дополнительно:

- Основная метрика выбора лучшей модели: MAE на validation
- Дополнительные метрики: RMSE, MAPE
- `window_size` для `GRU`: 56
- Batch size: 128
- Максимальное число эпох: 60 (с early stopping)
- Optimizer: Adam, weight_decay=1e-4
- Learning rate: 3e-4, расписание CosineAnnealingLR
- Как сохранялась лучшая модель: `model.state_dict()` при минимальном val_loss, восстанавливается после обучения

## 7. Анализ

Наивный baseline B1 ожидаемо оказался самым слабым (val_MAE = 20.34): предсказывать одно и то же значение для динамичного ряда с трендом и сезонностью неэффективно. B2 (скользящее среднее) улучшил результат вдвое (val_MAE = 12.66), так как учитывает локальную динамику последних 7 дней, однако всё равно игнорирует недельную сезонность и долгосрочные паттерны.

Ridge на лаговых признаках (B3) показал наилучший результат: val_MAE = 5.36. Богатый набор из 41 признака — лаги разной дальности, rolling-статистики, EWM, разности и календарные фичи — позволяет линейной модели явно закодировать и недельную сезонность, и тренд, и импульс. Это классический пример того, что при правильном feature engineering даже простая модель превосходит нейросеть.

GRU (R1) показала val_MAE = 6.37 — хуже Ridge. Это объяснимо: модель обучается только на сырых нормированных значениях без явных признаков, и 43 эпохи с ранней остановкой могут быть недостаточны для полного обучения на относительно небольшом train (~3000 примеров после нарезки окон). GRU имеет больший потенциал при более длинных рядах, сложной нелинейной динамике или мультивариантном входе.

Потенциальные утечки данных в задаче: использование `rolling` или `lag` без `shift` дало бы текущее значение таргета в признаках; `scaler.fit` на всём датасете передал бы статистику будущего в train; случайный split смешал бы будущее с прошлым. Все три источника утечки в данной работе устранены.

Выбор по validation, а не по test, принципиален: test — это имитация реального продакшна. Если смотреть на test при выборе модели, происходит неявная подгонка под него, и итоговая оценка перестаёт быть честной оценкой обобщающей способности.

## 8. Итоговый вывод

Для данной задачи Ridge на лаговых признаках является лучшим базовым подходом: он интерпретируем, быстро обучается и демонстрирует стабильные результаты. Простого baseline на признаках достаточно, когда структура ряда хорошо описывается линейными комбинациями лагов и rolling-статистик. Переходить к GRU имеет смысл при длинных мультивариантных рядах, явно нелинейной динамике или наличии внешних факторов, которые сложно закодировать вручную. Главный урок работы: корректная валидация по времени — это не деталь реализации, а принципиальное требование; любое нарушение хронологии делает метрики ненадёжными и может привести к деградации модели в продакшне.
